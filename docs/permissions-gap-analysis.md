# รายละเอียดสิ่งที่ต้องเพิ่ม: หน้าจอผู้ใช้งาน (User) และผู้ดูแลระบบ (Admin) ตามสิทธิ์
### ระบบบริหารจัดการเรื่องร้องเรียน สนง.กกต. (ECT Complaint Management System)

> ตรวจสอบจากซอร์สโค้ดจริงในโปรเจกต์ `C:\Developer\oect` (Next.js App Router) ไม่ใช่จากเอกสาร TOR อย่างเดียว เพื่อให้รายการที่ต้องเพิ่มตรงกับของจริงที่ทีมพัฒนาได้ทำไว้แล้ว

---

## 0. ข้อเท็จจริงพื้นฐานที่ต้องเข้าใจก่อน

โปรเจกต์นี้ **เป็น front-end prototype ล้วน ๆ ยังไม่มี backend จริง**:

- ไม่มีโฟลเดอร์ `app/api` แม้แต่ไฟล์เดียว
- ไม่มี `middleware.ts` — ไม่มีการกันสิทธิ์เข้าหน้า `/admin` หรือ `/user` เลย ใครพิมพ์ URL ตรง ๆ ก็เข้าได้ทันที
- `package.json` ไม่มี auth library (next-auth ฯลฯ) และไม่มี database client (prisma/postgres ฯลฯ)
- ข้อมูลเคสทั้งหมดเก็บใน **`localStorage` ของเบราว์เซอร์** ผ่าน `components/oect/useComplaintsStore.ts` (คีย์ `oect-cases-v1`) ไม่ได้อยู่บนเซิร์ฟเวอร์ ใครเปิด DevTools ก็แก้ไขข้อมูลเองได้ทันทีโดยไม่ผ่านสิทธิ์ใด ๆ
- หน้า Login (`app/login/page.tsx`) เป็น mock ทั้งหมด: กด submit แล้ว `setTimeout` แล้ว `router.push` ไม่มีการตรวจสอบ username/password/OTP/ThaID จริง และมีปุ่ม "ทดลองระบบ" ที่เข้าได้โดยไม่กรอกอะไรเลย

**ข้อสรุป:** รายการทั้งหมดด้านล่างนี้เป็น "ต้องสร้างใหม่" ทั้งฝั่ง UI ที่ยังขาด และฝั่ง backend ที่ยังไม่มีอยู่เลย สิทธิ์ที่บังคับแค่ฝั่ง client (ซ่อนปุ่ม/ซ่อนเมนู) ไม่มีความหมายด้านความปลอดภัยหากไม่มี server บังคับซ้ำ

## 1. โมเดลบทบาท (Role) ที่ขัดกันเองในโค้ด — ต้องเลือก/รวมก่อนเริ่มทำสิทธิ์จริง

พบว่ามี **โมเดล role อยู่ 2 ชุดคนละที่ ไม่ตรงกัน**:

| ชุดที่ 1 — 5 ระดับ (ใน `AdminSettingsView.tsx`, ไฟล์นี้ไม่ได้ถูกใช้งานจริง) | ชุดที่ 2 — 9 ระดับ (ใน `RoleWorkspaceView.tsx`, `OFFICER_ROLES` — **ใช้งานจริง**) |
|---|---|
| 1. พนักงานส่วนภูมิภาค | intake — พนักงานรับคำร้อง |
| | review-1 — พนักงานตรวจคำร้อง ชั้น 1 |
| | review-2 — พนักงานตรวจคำร้อง ชั้น 2 |
| 2. ผอ.สนง.กกต.จว. | director — ลธ./ผอ.สนง.กกต.จว. |
| | investigation — คณะกรรมการสืบสวนและไต่สวน |
| 3. กกต./ลธ.กกต. ส่วนกลาง | sequential — ผู้ตรวจสำนวนส่วนกลาง |
| | subcommittee — เลขาคณะอนุวินิจฉัย |
| | commission — กกต. |
| | secretary — ลธ.กกต. จัดทำคำวินิจฉัย |
| 4. ผู้ร้องเรียน | (แยกเป็นคนละ portal อยู่แล้ว) |
| 5. ผู้ดูแลระบบ (Admin) | admin — เห็นทุกขั้นตอน |

**ต้องทำ:** เลือกใช้ชุดเดียว แนะนำให้ใช้ **9 ระดับเป็นบทบาทปฏิบัติงานจริง (fine-grained)** เพราะผูกกับ SLA/ขั้นตอน workflow แล้ว แล้ว "จัดกลุ่ม" 9 ระดับนี้ให้ตกอยู่ใต้ 5 กลุ่มสิทธิ์ระดับสูง (สำหรับใช้ตั้งค่า permission matrix ภาพรวม/ใช้พรีเซนต์ผู้บริหาร) — ไม่ใช่สร้างสิทธิ์แยกกันคนละชุดแบบตอนนี้

## 2. ฝั่ง "หน้าจอผู้ใช้งาน" (`/user`) — แยกตามบทบาท

โครงสร้างหน้าปัจจุบัน: `app/user/page.tsx` สลับ 2 โหมดคือ **Citizen Portal** (`isCitizenPortal = true`) กับ **Officer Portal** (role ใน `OFFICER_ROLES`) โดยตอนนี้สลับผ่าน query string/dropdown เท่านั้น ไม่ผูกกับบัญชีจริง

### 2.1 พนักงานบันทึกข้อมูล / พนักงานตรวจคำร้อง (intake, review-1, review-2)

**มีอยู่แล้ว (UI เท่านั้น):** DashboardView, RoleWorkspaceView (คิวงานกรองด้วย `stageId`), CaseListView, CaseDetailModal, NewComplaintForm (mode officer), SlaMonitoringView, WorkflowVisualizer

**ต้องเพิ่ม:**
1. **กรองข้อมูลตามจังหวัด/หน่วยงานที่สังกัดจริง** — ปัจจุบัน `RoleWorkspaceView.tsx` กรองเฉพาะ `ROLE_STAGE_IDS[roleId]` (ตามขั้นตอน) เท่านั้น ไม่กรองตามจังหวัด พนักงานเชียงใหม่เห็นเคสของทุกจังหวัดปนกันหมด ต้องเพิ่ม field "จังหวัด/หน่วยงานที่สังกัด" ผูกกับบัญชีผู้ใช้ แล้ว filter คิวงานด้วย
2. **จำกัดสิทธิ์แก้ไขเฉพาะเคสที่ตัวเองรับผิดชอบ** — ตอนนี้ `CaseDetailModal.tsx` เปิดให้กด "บันทึกคำสั่ง/ความเห็น" ได้กับทุกเคสไม่ว่าใครเปิด ไม่มีการเช็คว่าเป็นผู้รับผิดชอบเคสนั้นจริงหรือไม่
3. **จำกัดตัวเลือกคำสั่งในแท็บ "บันทึกคำสั่ง" ให้ตรงกับ stage/role** — จุดนี้สำคัญมาก: ใน `CaseDetailModal.tsx` (บรรทัด action tab) dropdown คำสั่งแสดง **ทุกคำสั่งของทุกขั้นตอนรวมกัน** (ตั้งแต่ "สั่งรับคำร้อง" ไปจนถึง "บันทึกมติที่ประชุม กกต. วินิจฉัยชี้ขาด") ไม่ว่าใครเปิดเคสไหนก็เห็นครบทุกตัวเลือก ต้องกรองให้เหลือเฉพาะคำสั่งที่ role/stage ปัจจุบันมีสิทธิ์สั่งจริง มิฉะนั้นพนักงานรับคำร้องจะกดคำสั่งของ กกต. ได้ตรง ๆ
4. **ปุ่ม "แจ้งผู้ร้องแก้ไขเพิ่มเติม" ตามข้อ 26(2) ของระเบียบ** (กรณีรายการไม่ครบถ้วน) — ยังไม่มี action นี้ในดรอปดาวน์ปัจจุบัน
5. **ฟิลด์ "ผู้รับมอบหมาย/ผู้รับผิดชอบ" เป็นความสัมพันธ์กับบัญชีผู้ใช้จริง** — ตอนนี้ `officer` ใน `data/complaintsData.json` เป็นแค่ string ชื่อเฉย ๆ ไม่ผูกกับบัญชี ทำให้ "มอบหมายงาน" ไม่สามารถทำได้จริงในระบบ (แค่ตัวหนังสือ)
6. **บันทึก Audit log ระดับ action จริง** (ใครกดอะไร เวลาไหน ไอพีอะไร) — ตอนนี้ `handleSaveAction` ใน `CaseDetailModal.tsx` แค่ `alert()` ไม่บันทึกอะไรเลย

### 2.2 ผอ.สนง.กกต.จว. (director)

**มีอยู่แล้ว:** เข้าถึงหน้าเดียวกับพนักงาน (RoleWorkspaceView กรอง stage 2,4), CaseListView, Dashboard

**ต้องเพิ่ม:**
1. **หน้าจอ Dashboard เฉพาะจังหวัดตนเอง** (ตาม TOR ข้อ ๔.๓) — ปัจจุบัน `DashboardView.tsx` แสดงภาพรวมทั้งประเทศเหมือนกันทุก role ไม่มีเวอร์ชันกรองเฉพาะจังหวัด
2. **สิทธิ์ "สั่งรับ/ไม่รับ/ยกคำร้อง"** ต้องผูกกับ dropdown คำสั่งใน CaseDetailModal ให้เฉพาะ role นี้เห็น (ดูข้อ 2.1.3)
3. **หน้าจอมอบหมายงานให้พนักงานในจังหวัดตนเอง** — ยังไม่มี UI ให้เลือก "มอบหมายให้ใคร" เป็นการ action จริง (มีแค่ field officer แบบ static)
4. **ปุ่มขออนุมัติขยายเวลาสืบสวน (15+15 วัน)** ตามข้อ 41 ว.3 — มีอยู่ในดรอปดาวน์ command กลางแล้ว แต่ต้องแยกให้ชัดว่าใครสั่งได้ และต้องมี "เหตุผลการขยาย" + ผู้อนุมัติ (ลธ./ผอ.) เป็น workflow ย่อยของตัวเอง ไม่ใช่แค่ตัวเลือกในดรอปดาวน์เดียว

### 2.3 กกต./ลธ.กกต. ส่วนกลาง (sequential, subcommittee, commission, secretary)

**มีอยู่แล้ว:** RoleWorkspaceView กรอง stage 5-9, Dashboard, WorkflowVisualizer

**ต้องเพิ่ม:**
1. **Dashboard ภาพรวมทั้งประเทศแยกต่างหากจากจังหวัด** (ให้ตรงกับ scope สิทธิ์ "เห็นทั่วประเทศ")
2. **หน้าจอคณะอนุวินิจฉัย** ตาม TOR (ข้อ ๔.๔) ที่ต้องมี "นัดประชุม", "ทำธุรการยืมเงิน", "ทำความเห็น" แยกเป็นสถานะย่อย — ตอนนี้มีแค่ 1 status รวมในดรอปดาวน์ ("เสนอความเห็นต่อคณะอนุวินิจฉัย") ไม่มีหน้าจอย่อยของคณะอนุฯ
3. **สิทธิ์ "วินิจฉัยชี้ขาด" ต้องแยกจากสิทธิ์ "จัดทำคำวินิจฉัย"** (ข้อ 84) เพราะ TOR ระบุว่าเป็นคนละบทบาท/คนละ SLA (กกต. วินิจฉัยชี้ขาด 90 วัน vs ลธ. จัดทำคำวินิจฉัย 60 วัน) — โค้ดปัจจุบันรวม role "secretary" คือ "ลธ.กกต. จัดทำคำวินิจฉัย" ไว้แยกแล้ว แต่ยังไม่มีการบังคับว่า role "commission" (กกต.) ต้องอนุมัติก่อนถึงจะเข้า stage "secretary" ได้ (ไม่มี state machine บังคับลำดับ)
4. **แจ้งมติเบื้องต้นให้ ผอ. เพื่อแจ้งผู้ร้อง/ผู้ถูกร้อง** (ภายใน 15 วัน) — ยังไม่มี action ส่งแจ้งกลับไปยังจังหวัดเป็น workflow ย้อนกลับ มีแค่ปิดเรื่อง

### 2.4 ผู้ร้องเรียน (Citizen Portal)

**มีอยู่แล้ว:** `CitizenServiceView.tsx` มี 7 แท็บครบ (หน้าหลัก, ยื่นคำร้องใหม่, ติดตามสถานะ, แก้ไขคำร้อง, ผลการพิจารณา, ประวัติของฉัน, โปรไฟล์), `CitizenTrackingView.tsx`, `NewComplaintForm` mode citizen, `CaseDetailModal` แบบ `readOnly`

**ต้องเพิ่ม:**
1. **การยืนยันตัวตนกรณีมอบอำนาจ** — TOR ระบุว่า "ยื่นด้วยตนเอง/มอบอำนาจ" ได้ (ข้อ 25) แต่หน้าจอผู้ร้องเรียนปัจจุบันผูกกับ `CURRENT_CITIZEN` คนเดียวคงที่ ไม่มี flow สำหรับกรณีมอบอำนาจ (ใครยื่นแทนใคร ต้องแนบหนังสือมอบอำนาจ)
2. **แท็บ "แก้ไขคำร้อง"** (correction) — ต้องเช็คว่า flow เชื่อมกับ action "แจ้งผู้ร้องแก้ไขเพิ่มเติม" ของเจ้าหน้าที่จริงหรือไม่ (ตอนนี้ทั้งสองฝั่งยังไม่เชื่อมกัน เพราะเจ้าหน้าที่ยังไม่มีปุ่มนี้ตามข้อ 2.1.4)
3. **สิทธิ์ดูเฉพาะเคสของตนเอง จริง ๆ ที่ backend** — ตอนนี้กรองด้วย `cases.filter(item => item.complainants.includes(CURRENT_CITIZEN.name))` ฝั่ง client เท่านั้น (ทุกเคสอยู่ใน localStorage เดียวกันหมด ไม่มีการแบ่งข้อมูลจริงตาม user)
4. **การแจ้งเตือนอัตโนมัติ** (ใกล้ครบ/เกินกำหนด ผ่าน SMS/อีเมล) — ตอนนี้มีแค่ badge ตัวเลขในกระดิ่ง ไม่มีการส่งแจ้งเตือนจริงออกนอกระบบ

## 3. ฝั่ง "ผู้ดูแลระบบ" (`/admin`) — ตามเมนูที่มีอยู่จริงในโค้ด

`app/admin/page.tsx` มี 10 เมนู: ภาพรวมระบบ, รายการเรื่องร้องเรียน, คิวงานทุกขั้นตอน, ติดตาม SLA, รายงานและ Audit, **ผู้ใช้และสิทธิ์**, Workflow และ SLA, ข้อมูลพื้นฐาน, ระบบเชื่อมโยง, Security และ Audit

### 3.1 เมนู "ผู้ใช้และสิทธิ์" (`UsersPanel` ใน `app/admin/page.tsx`) — ช่องว่างใหญ่ที่สุด

สถานะปัจจุบัน: ดึงชื่อจาก field `officer` ในข้อมูลเคสมาแสดงเป็นรายชื่อ "คนที่เคยรับผิดชอบ" เท่านั้น — โค้ดเองมีข้อความกำกับตรง ๆ ว่า **"ไม่ใช่ฐานบัญชี Identity Provider"**

**ต้องเพิ่มทั้งหมด (ยังไม่มีอะไรทำงานจริงสักปุ่ม):**
1. ปุ่ม **เพิ่มผู้ใช้งานใหม่** (กรอกชื่อ, บัญชี, อีเมล, เบอร์โทร, จังหวัด/หน่วยงานที่สังกัด, กำหนด role จาก 9 ระดับ)
2. ปุ่ม **แก้ไข/ระงับการใช้งาน/ลบบัญชี**
3. ปุ่ม **รีเซ็ตรหัสผ่าน** และ **ปลดล็อคบัญชี** ที่ถูกล็อคจาก login ผิดหลายครั้ง
4. **ตาราง Role Permission Matrix จริง** (มีต้นแบบอยู่แล้วใน `components/oect/AdminSettingsView.tsx` แต่ไม่ได้ต่อสายเข้ามาใช้ — ต้องนำมาเชื่อมกับเมนูนี้ แล้วขยายจาก 5 ระดับให้ครอบคลุม 9 role ย่อยที่ใช้งานจริง)
5. **ผูก user เข้ากับจังหวัด/หน่วยงาน** เพื่อใช้เป็น data scope filter (ดูข้อ 2.1.1 และ 2.2.1)
6. Field เก็บ **ประวัติการเข้าใช้งานล่าสุด** (last login) ต่อบัญชี

### 3.2 เมนู "Security และ Audit" (`SecurityPanel`)

สถานะปัจจุบัน: แสดงเป็น "การ์ดสถานะ" คงที่ (Authentication, Session, Data encryption ฯลฯ) ที่เป็น**ข้อความ hardcode ไม่ได้อ่านค่าตั้งค่าจริงจากไหนเลย** และ "Data & audit coverage" เป็นแค่ % ของฟิลด์ที่กรอกครบในข้อมูลเคส ไม่ใช่ audit log จริง

**ต้องเพิ่ม:**
1. หน้าตั้งค่านโยบายจริง ที่แก้ไขได้ (เปิด/ปิดบังคับ 2FA, ตั้งเวลา auto-logout, ตั้งนโยบายรหัสผ่าน)
2. **Audit log ตัวจริง** ที่บันทึกทุก action (login/logout, ดูข้อมูล, แก้ไข, อนุมัติ, เปลี่ยนสิทธิ์) พร้อม timestamp, user, IP — เก็บแบบ append-only แก้ไข/ลบย้อนหลังไม่ได้ตามที่ระบุใน UI (ตอนนี้ยังไม่มีของจริง มีแค่ mock 4 แถวใน `AdminSettingsView.tsx` ที่ไม่ได้ใช้งานอยู่ดี)
3. ปุ่ม **Export audit log** สำหรับตรวจสอบ/ส่งหน่วยงานกำกับดูแล

### 3.3 เมนู "Workflow และ SLA" (`WorkflowPanel`)

สถานะปัจจุบัน: แสดงรายการ 10 ขั้นตอนจาก `WORKFLOW_STEPS` (hardcode ในโค้ด) แบบ read-only ปุ่ม "ตรวจสอบ" แค่ขึ้น toast ไม่ได้แก้ไขอะไรจริง

**ต้องเพิ่ม:**
1. ฟอร์มแก้ไขจำนวนวัน SLA ต่อขั้นตอนได้จริง (มีต้นแบบ UI อยู่แล้วใน `AdminSettingsView.tsx` tab "ตั้งค่า SLA" แต่ยังไม่ผูก state/ไม่บันทึกจริง)
2. ระบบ **versioning ของ workflow** — แก้ไขกฎใหม่ไม่กระทบสำนวนที่กำลังดำเนินการอยู่ (ตามที่ระบุใน eyebrow ของหน้านี้เองว่า "โดยไม่เปลี่ยนกฎกลางสำนวนที่กำลังดำเนินการ" แต่ยังไม่มีกลไกรองรับจริง)
3. **สิทธิ์จำกัดเฉพาะ Admin** ในการแก้ไข workflow/SLA — ต้องผูกกับ permission matrix ข้อ 3.1.4

### 3.4 เมนู "ข้อมูลพื้นฐาน" (`MasterDataPanel`)

สถานะปัจจุบัน: แสดงสถิติที่คำนวณจากข้อมูลเคสที่มีอยู่ (เช่น "7 จังหวัดในชุดข้อมูล") ปุ่ม "จัดการข้อมูล" ไม่ทำงาน (ไม่มี onClick)

**ต้องเพิ่ม:** หน้าจอ CRUD จริงสำหรับจังหวัด/อำเภอ/ตำบล/เขตเลือกตั้ง/ประเภทคำร้อง/แบบฟอร์มมาตรฐาน (สตว.1, สตว.1/1) — ควรจำกัดสิทธิ์แก้ไขเฉพาะ Admin เช่นกัน

### 3.5 เมนู "ระบบเชื่อมโยง" (`IntegrationsPanel`)

สถานะปัจจุบัน: การ์ดสถานะ "Online" คงที่ ปุ่ม "ตรวจสอบการเชื่อมต่อ" แค่ขึ้น toast ไม่ได้ยิง request จริง

**ต้องเพิ่ม:** การตั้งค่า endpoint/certificate/retry policy จริงของ DXC, e-Saraban, PRAXTICOL พร้อมสิทธิ์จำกัดเฉพาะ Admin ในการแก้ไขค่าเชื่อมต่อ (เพราะเป็นข้อมูลอ่อนไหวด้านความปลอดภัย)

## 4. สิ่งที่ต้องเพิ่มร่วมกันทั้งระบบ (Cross-cutting — ทำก่อนอย่างอื่นทั้งหมด)

รายการนี้เป็นรากฐานที่ทุกข้อข้างบนต้องพึ่งพา ถ้าไม่ทำ สิทธิ์ที่ออกแบบทั้งหมดจะเป็นแค่การซ่อนปุ่มในหน้าเว็บเท่านั้น ไม่ใช่ระบบรักษาความปลอดภัยจริง:

1. **สร้าง Backend + Database จริง** (แทน localStorage) — API routes (`app/api/...`) หรือ backend service แยก พร้อมฐานข้อมูลเก็บ users, roles, permissions, cases, audit_logs
2. **ระบบ Authentication จริง** — ตรวจ credential, ออก session/JWT, เชื่อมต่อ ThaID API จริง (ตอนนี้เป็นปุ่ม "จำลองการยืนยัน ThaID สำเร็จ")
3. **Route guard / Middleware** — กัน `/admin`, `/user` ไม่ให้เข้าได้โดยไม่ login และเช็คว่า role ที่ login มามีสิทธิ์เข้าหน้านั้นจริง
4. **Authorization ฝั่ง server** สำหรับทุก action (ไม่ใช่แค่ซ่อนปุ่มฝั่ง UI) — ตรวจสิทธิ์ก่อนบันทึกทุกครั้งที่ API
5. **Data scope filter ที่บังคับจาก server** ตามจังหวัด/หน่วยงานของผู้ใช้ที่ login (ไม่ใช่ filter ฝั่ง client ที่ผู้ใช้แก้เองได้)
6. **Audit log กลางที่บันทึกทุก request** (ไม่ใช่ mock data ที่เห็นตอนนี้)

## 5. ตาราง Checklist สรุปลำดับความสำคัญ

| ลำดับ | รายการ | ผลกระทบถ้าไม่ทำ | ความซับซ้อน |
|---|---|---|---|
| 1 | Backend + Database จริง (แทน localStorage) | สิทธิ์ทั้งหมดไม่มีผลจริง แก้ไขข้อมูลเองได้จาก DevTools | สูง |
| 2 | Authentication จริง + Route guard | ใครก็เข้าทุกหน้าได้โดยไม่ login | สูง |
| 3 | เชื่อม `AdminSettingsView.tsx` (Permission Matrix) เข้าเมนู "ผู้ใช้และสิทธิ์" จริง + ขยายเป็น 9 role | ไม่มีจุดกำหนดสิทธิ์ตามบทบาทเลยสักที่ | กลาง |
| 4 | กรองคำสั่งในแท็บ "บันทึกคำสั่ง" (CaseDetailModal) ตาม role/stage | เจ้าหน้าที่ระดับล่างสั่งการแทนกกต.ได้ตรง ๆ | กลาง |
| 5 | Data scope filter ตามจังหวัด | ผอ.จังหวัดหนึ่งเห็นข้อมูลจังหวัดอื่นทั้งหมด | กลาง |
| 6 | Audit log จริง (ผูก backend) | ตรวจสอบย้อนหลังไม่ได้ ขัดหลัก PDPA/ROPA ที่อ้างไว้ใน UI | กลาง |
| 7 | ผูก "ผู้รับผิดชอบ/มอบหมายงาน" เป็นความสัมพันธ์กับบัญชีจริง | มอบหมายงานได้แค่ในทางทฤษฎี (เป็น string) | กลาง |
| 8 | Workflow/SLA config ที่บันทึกได้จริง + versioning | แก้ SLA ไม่ได้จริง กระทบสำนวนที่ค้างอยู่ถ้าทำไม่ดี | กลาง |
| 9 | หน้าจอย่อยคณะอนุวินิจฉัย + แยกสิทธิ์วินิจฉัย/จัดทำคำวินิจฉัย | ขั้นตอนสำคัญตาม TOR ยังไม่มีหน้าจอรองรับ | กลาง |
| 10 | Flow มอบอำนาจฝั่งผู้ร้องเรียน + เชื่อม "แก้ไขคำร้อง" กับฝั่งเจ้าหน้าที่ | ผู้ร้องมอบอำนาจยื่นไม่ได้ตามที่ระเบียบอนุญาต | ต่ำ-กลาง |
